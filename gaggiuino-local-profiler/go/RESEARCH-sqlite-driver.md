# SQLite driver evaluation — modernc vs. ncruces (spike #958)

Decision doc for GitHub issue #958 (closed). Only this doc was kept; the
benchmark harness (`internal/db/driver_bench_test.go` behind the
`driverbench` build tag, plus the throwaway `ncruces/go-sqlite3` require in
`go.mod`) was not brought over — it stays recoverable from the spike commit
`c98983b` on the retired `spike/sqlite-driver-958` branch.

Reproduce (from that commit):

```
go test -tags driverbench -run '^$' -bench . -benchmem ./internal/db/
go test -tags driverbench -run TestSpikeColdStartModernc -v ./internal/db/
go test -tags driverbench -run TestSpikeColdStartNcruces  -v ./internal/db/
```

## TL;DR — keep `modernc.org/sqlite`

The swap is genuinely near-drop-in and ncruces wins on concurrent-reader
throughput, but it does **not** move the needle on #957's actual problem
(the cost of a full blob scan is Go-side JSON hydration — 110 MB / ~150k
allocs per scan — not the driver), and it costs +3–5 MB of binary, ~+30 %
cold build time, one fiddly test port, and a new dependency. Do #957's
algorithmic work first. Revisit ncruces only if a profiled hot path still
does a large *concurrent* blob scan afterwards — then the +59 % concurrent
read number earns the switch and it's a half-day job. cgo via `zig cc` is
not warranted at all.

## What was compared

| | in use today | candidate |
|---|---|---|
| module | `modernc.org/sqlite v1.57.0` | `github.com/ncruces/go-sqlite3 v0.34.0` |
| engine | SQLite C transpiled to Go (`ccgo`) | SQLite C → wasm → Go (`wasm2go`, module `go-sqlite3-wasm/v2`) |
| cgo | no | no |
| wazero / wasm runtime at runtime | no | **no** (see note) |
| driver name | `sqlite` | `sqlite3` |

**Important architecture note.** The issue text ("real SQLite compiled to
WASM (wazero)") describes ncruces as it was up to ~v0.28. **v0.34 does not
depend on wazero at all** — `go-sqlite3-wasm/v2` is the wasm build
transpiled to plain native Go (`// Code generated by wasm2go`), the same
execution model as modernc. So there is no wasm interpreter and no
"interpreter fallback on architectures wazero can't JIT" — the armv7 risk
that motivated this spike does not exist for current ncruces. (`wazero
v1.4.0` stays in `go.mod` as an indirect dep, but only because
`kanrichan/resvg-go` pulls it.)

## Micro-benchmark results

Host: linux/amd64, Intel i3-8145U @ 2.10 GHz. Dataset: **5000 shots**, each
with a realistic `datapoints` blob (8 series, 90–310 samples, JSON
5–15 KB, ~10 KB mean), `annotations` on every 5th shot. Both drivers:
`journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`,
`synchronous=NORMAL`, pool size 4 (12 for the concurrency test). ncruces
additionally gets `_txlock=immediate` (its documented recommendation for a
writing `database/sql` pool).

| scenario | modernc v1.57.0 | ncruces v0.34.0 | verdict |
|---|---|---|---|
| **Full-table scan** — 5000 rows, read blob, decode JSON top level (≈ `Repository.FindAllExcludingTrash` + `hydrateRow`) | **362 ms/op**, 110 MB/op, 151 774 allocs/op | **335 ms/op**, 110 MB/op, 162 773 allocs/op | ncruces ~7 % faster wall, ~7 % more allocs — within noise |
| **Single-row `FindByID`** — indexed `WHERE s.id = ?` + hydrate | **119 µs/op**, 54 allocs | **114 µs/op**, 57 allocs | tie |
| **8 readers + 1 writer**, 2 s window — read throughput | **52 500 reads/s** | **83 700 reads/s** | **ncruces +59 %** |
| — `SQLITE_BUSY` seen (either side) | 0 | 0 | tie (WAL + busy_timeout works for both) |
| **Cold start** — first `sql.Open` + first query, fresh process | **548 µs** | **900 µs** | ncruces +~350 µs, one-time per process |

Takeaways:

- **Scan speed is a wash.** 7 % on wall time, both ~110 MB and ~150k
  allocs per scan — that allocation load is the JSON hydration in
  `hydrateRow`, which is identical Go code regardless of driver. Swapping
  the driver does not help #957; only scanning fewer blob rows does.
- **Concurrent reads are where ncruces is genuinely better** (+59 %). Real
  SQLite's page cache / WAL reader path beats the transpiled-C one under
  contention. This is the one result that could justify a switch — but
  #956 already removed the single-connection head-of-line block, and the
  achievements full scan is now change-fingerprint-gated (#956), so the
  app has far fewer concurrent blob scans than it used to.
- **Cold start delta is negligible** (~0.35 ms, paid once at process
  start). No wazero JIT warm-up because there is no wazero.

## Build & binary size impact

`CGO_ENABLED=0`, `GOOS=linux`, `-trimpath -ldflags="-s -w"`, placeholder
frontend embed. All three target arches cross-compile cleanly with **both**
drivers (`go test -tags driverbench -c` for the test binary that actually
links ncruces: amd64 / arm64 / arm all OK).

| target | modernc | ncruces | delta |
|---|---|---|---|
| linux/amd64 | 18.87 MB | 23.10 MB | **+4.23 MB** |
| linux/arm64 (aarch64) | 17.83 MB | 21.17 MB | **+3.34 MB** |
| linux/arm/v7 (armv7) | 18.15 MB | 23.59 MB | **+5.44 MB** |

- Cold-cache full `./cmd/server` build: **71 s → 93 s** (+~30 %). The
  `wasm2go` output is a single ~6 MB generated `.go` file. One-time cost —
  CI keeps a Go build cache and the driver source never changes on
  feature work.
- New modules pulled in (after `go mod tidy`): just 3 —
  `ncruces/go-sqlite3`, `ncruces/go-sqlite3-wasm/v2`, `ncruces/julianday`.
  wazero is **not** added.
- **Go toolchain:** ncruces **v0.34.x** requires `go >= 1.25.0` — matches
  the current `go.mod` directive exactly, no bump. **v0.35.0+ jumped to
  `go >= 1.26.0`** — a switch would have to pin `v0.34.x` until the
  project is ready to move the directive to 1.26.

## 32-bit caveat (armv7)

ncruces caps SQLite's memory arena when `bits.UintSize < 64`:
`createWrapper` sets `mem.Max = 512` pages = **32 MB per connection** on
armv7 (256 MB on 64-bit). Comfortably enough for this workload (a full
5000-shot scan streams rows, it doesn't materialise the DB in the arena),
but it is a hard ceiling modernc does not have. Worth a load test on real
armv7 hardware before any switch, given armv7 is already the
least-exercised target.

## DSN / code migration effort — small

`internal/db/db.go`:

```go
- _ "modernc.org/sqlite"
+ _ "github.com/ncruces/go-sqlite3/driver"     // registers "sqlite3", no embed import needed in v0.34
...
- sqlDB, err := sql.Open("sqlite", dsn)
+ sqlDB, err := sql.Open("sqlite3", dsn)
```

- The DSN string is **unchanged**: ncruces parses the same
  `?_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)&_pragma=foreign_keys(ON)&_pragma=synchronous(NORMAL)`
  syntax verbatim. Optionally add `&_txlock=immediate`.
- `SetMaxOpenConns(>1)` + WAL concurrent readers: **works** — the existing
  `pool_test.go` (`TestOpen_PoolAppliesPragmasToEveryConnection`,
  `TestOpen_ConcurrentReadersDoNotBlock`, `TestOpen_ReaderAndWriterNoSQLiteBusy`)
  all pass unchanged against ncruces (verified in this spike).
- The doc comment in `db.go` explains modernc-specific `_pragma` semantics
  — needs a rewrite, not just a rename.

| file | change | size |

## cgo via `zig cc` — not warranted

`mattn/go-sqlite3` + `zig cc` cross-compilation would give the fastest
driver, but:

- The bottleneck this spike found on the scan path is **Go-side JSON
  hydration**, which cgo does not touch.
- ncruces already delivers real-SQLite runtime characteristics (that +59 %
  concurrent-read result) with **no cgo, no build-system change**. If
  pure-Go SQLite ever becomes the actual bottleneck, ncruces is the next
  step — cgo is the step after that, and only if a profile proves the
  SQLite engine itself (not the surrounding Go) is the hot spot.
- cgo reintroduces exactly the multi-arch C-compile pain the Go rewrite
  removed (see the repo-root Node `Dockerfile`'s `prod-deps` QEMU comment).

## Recommendation

1. **Keep `modernc.org/sqlite`.** Ship #957's algorithmic fixes
   (incremental achievements, kill remaining full-blob scans on hot
   paths). That removes the constant-factor sensitivity entirely.
2. **Re-benchmark after #957.** If a profiled request still does a large
   concurrent blob scan, switch to `ncruces/go-sqlite3 v0.34.x` — the
   +59 % concurrent-read win is real, the port is ~half a day, and it
   stays cgo-free / single-static-binary / all three arches. Load-test
   armv7 first (32 MB arena cap).
3. **Do not pursue cgo / `zig cc`.**
